Проект следует правилам Google Java Style Guide с адаптацией.

### 1. Именование методов: camelCase
До:    public void add_student(Student s) { }
После: public void addStudent(Student student) { }
Почему: Java Convention требует camelCase для методов.
Источник: https://google.github.io/styleguide/javaguide.html#s5.3-camel-case

### 2. Пробелы после if/for/while
До:    if(condition) {
После: if (condition) {
Почему: улучшает читаемость, отделяет ключевое слово от выражения.
Источник: Oracle Code Conventions — Whitespace

### 3. Длина строки: максимум 100 символов
До:    public List getStudentsFromSpecificCityWithVeryLongName...
После: public List getStudentsByCity(String city) {
Почему: длинные строки затрудняют чтение в редакторе и при code review.
Источник: https://google.github.io/styleguide/javaguide.html#s4.4-column-limit

### 4. Порядок импортов
До:    import java.util.List; import java.util.ArrayList; import java.io.File;
После: import java.io.File; import java.util.ArrayList; import java.util.List;
Почему: алфавитный порядок упрощает поиск импортов.
Источник: `config/checkstyle/checkstyle.xml` (`CustomImportOrder`) и проектная схема `.idea/codeStyles/Project.xml`

### 5. Фигурные скобки для if
До:    if (condition) doSomething();
После: if (condition) { doSomething(); }
Почему: скобки обязательны даже для однострочных блоков.
Источник: https://google.github.io/styleguide/javaguide.html#s4.1.1-braces-always-used

### 6. Использование двух пробелов вместо табуляции
До:      (TAB) public List getStudentsByCity(String city) {
После:   (2 spaces) public List getStudentsByCity(String city) {
Почему: каждый раз когда открывается новый блок отступ увеличивается на два пробела
Источник: https://google.github.io/styleguide/javaguide.html#s4.2-block-indentation

### 7. Импорт без wildcards
До:      import java.util.*;
После:   import java.util.List;
Почему: делают код менее предсказуемым, могут незаметно менять поведение при обновлении библиотек, замедляют чтение и ломают инструменты
Источник: https://google.github.io/styleguide/javaguide.html#s3.3.1-wildcard-imports

## Ответ
## Шаг 1. Закрыть границу порога `readyForSprint`

**Что проверить:** значение `plannedHoursPerWeek`, равное ровно **3**.

**Почему это важно:** у тебя в тестах уже есть «выше порога» (4 → true) и «ниже порога» (2 → false). Но само граничное значение 3 не проверено. В коде условие `>= 3`, и именно на границе чаще всего прячутся ошибки: если кто-то случайно поменяет `>=` на `>`, тесты с 4 и 2 всё равно пройдут, а поведение сломается. Граничные значения — классический источник багов, и их обязательно покрывают.

**Что покрывает:** ветку `plannedHoursPerWeek >= 3` на самой границе.

## Шаг 2. Проверить экстремальные и нестандартные значения часов

**Что проверить:** `plannedHoursPerWeek` = **0**, отрицательное число (например, `-1`), очень большое (`Integer.MAX_VALUE`).

**Почему это важно:** сейчас в `MenteeProgress` **нет валидации** полей. Record принимает любое `int`. Поведение с 0 и отрицательными значениями не определено тестами — а оно может быть неожиданным: `0 >= 3` = false, `-5 >= 3` = false. Если бизнес-логика предполагает, что часы не могут быть отрицательными, это должно быть зафиксировано тестом (либо проверкой в конструкторе, либо ожиданием false). Большие значения проверяют, что нет переполнения и логика не ломается на `MAX_VALUE`.

**Что покрывает:** поведение при выходе за «разумный» диапазон; документирует контракт класса.

## Шаг 3. Проверить `summary()` на разных входных данных

**Что проверить:** формат строки при:

- `sprintNumber` = 0 или отрицательном;
- имени с пробелами, дефисами, кириллицей (уже частично есть «Ирина», но можно добавить составное имя);
- **пустом имени** (`""`);
- `plannedHoursPerWeek` = 0.

**Почему это важно:** текущий тест проверяет только один «счастливый» случай (`Ирина, 1, 8`). Но `summary()` использует `String.formatted`, и любое изменение формата или нестандартные данные могут дать неожиданный результат. Например, пустое имя даст `"Sprint 1 → : planned 8 h"` — выглядит криво, но так работает. Тест **фиксирует это поведение**, чтобы при будущем рефакторинге ты осознанно решил, менять его или нет. Плюс проверка отрицательного `sprintNumber` — вдруг формат не рассчитан на такое.

**Что покрывает:** стабильность формата; разные комбинации данных; документирует текущее поведение для граничных случаев.

## Шаг 4. Проверить согласованность `summary()` и `readyForSprint()`

**Что проверить:** для одного и того же объекта оба метода возвращают непротиворечивую информацию.

**Почему это важно:** это **интеграционная проверка** между двумя методами. Если `readyForSprint()` вернул `true`, то в `summary()` должно быть число часов `>= 3`. Наоборот — если `false`, то `< 3`. Это свойство инварианта класса: два публичных метода не должны противоречить друг другу. Такой тест ловит ошибки, которые не видны при проверке каждого метода по отдельности.

**Что покрывает:** связь между методами; инвариант «часы в summary совпадают с решением readyForSprint».

## Шаг 5. Проверить поведение record: аксессоры, `equals`, `hashCode`

**Что проверить:**

- аксессоры (`menteeName()`, `sprintNumber()`, `plannedHoursPerWeek()`) возвращают то, что передали в конструктор;
- два `MenteeProgress` с одинаковыми полями равны (`equals`), и у них одинаковый `hashCode`;
- объекты с разными полями — не равны.

**Почему это важно:** record **автоматически генерирует** эти методы, и они тоже входят в подсчёт покрытия JaCoCo. Если их никогда не вызывать, они «висят» в непокрытых инструкциях. Плюс `equals`/`hashCode` — это контракт, который часто используется в коллекциях (`Set`, `Map`), и его стоит зафиксировать тестом. Заодно проверяется, что конструктор действительно сохранил все поля, а не потерял что-то.

**Что покрывает:** автогенерируемые методы record; корректность конструктора; контракт равенства.

## Общие принципы, почему именно эти кейсы

- **Границы** (`3`, `0`) — самое частое место ошибок.
- **Негативные сценарии** (отрицательные значения, пустая строка) — проверяют, что код не падает и ведёт себя предсказуемо.
- **Согласованность между методами** — ловит логические ошибки, которые не видны при изолированных тестах.
- **Автогенерируемые методы record** — покрывают код, который тоже считается в JaCoCo, но обычно остаётся без тестов.
- **Документирование текущего поведения** — если поведение нежелательное (например, пустое имя даёт кривую строку), тест заставляет принять решение: чинить или принять как есть.

После реализации этих кейсов `MenteeProgress` будет полностью покрыт по инструкциям, а контракт класса — зафиксирован явно.

## 1. Логические ошибки и граничные случаи

### 1.1. `mentees == null` → `NullPointerException`

**Проблема.** Первое же обращение `mentees.length` при `mentees == null` бросит NPE. Сообщение будет неинформативное — непонятно, что именно пришло `null`.

**Почему важно.** Если метод публичный и вызывается извне, откуда угодно может прилететь `null`. Падать с голым NPE без контекста — плохо для отладки и для вызывающей стороны.

**Как исправить.** В начале метода — проверка:

- либо вернуть осмысленный результат (`"Суммарно: пройдено 0 из 0 уроков, осталось 0 уроков"`),
- либо бросить `IllegalArgumentException("mentees must not be null")` — это явнее, чем NPE.

Второй вариант обычно предпочтительнее: невалидный вход должен быть явно отвергнут.

### 1.2. `mentees` содержит `null` → `NullPointerException`

**Проблема.** Даже если сам массив не `null`, внутри может лежать `null`-элемент. Тогда `mentees[index].completedLessons()` бросит NPE.

**Почему важно.** Массив — это «дырявая» структура, никто не гарантирует отсутствие `null` внутри. Особенно если его формируют снаружи.

**Как исправить.** Варианты:

- проверять каждый элемент на `null` и **пропускать** его;
- проверять и **бросать** `IllegalArgumentException` с указанием индекса;
- использовать `Objects.requireNonNull` в конструкторе `Mentee` — но это уже про другой класс.

Выбор зависит от контракта: «null не допускается вообще» или «null просто игнорируется».

### 1.3. Пустой массив — технически работает, но не проверен

**Почему важно.** Метод молча полагается на инвариант другого класса. Это скрытая зависимость: изменение в `Mentee` сломает `ProgressTracker` без предупреждения.
